## 一、设计概念

### 1.1 五个功能，其实是一个动作

需求写的是「截图、录屏、剪贴板管理、贴图、AI token 用量分析」五项融合。按功能各画一个符号拼起来，在 16px 下必然糊成一团——而且那也不是「融合」，是「并列」。

它们真正共同的地方是**时间上的同一件事**：

```
      取（take）                   留（keep）              累积（accrue）
  截图 ─┐                    ┌─ 贴图贴在桌面上        ┌─ 剪贴板历史
  录屏 ─┼─ 同一个「拉一块」手势 ─┤                       ┤
       ┘                    └─ 命名 / 存盘          └─ AI token 用量记录
```

所以图标只画这一件事：**一块被取下来的区域，以及落在它上面的那道记号**。三个方向的区别是「谁当主角」：

| 方向 | 主角 | 一句话 |
|---|---|---|
| **A · 取景框上的记号** `MARK ON FRAME` | 被取下的**区域** | 截图与录屏是同一个手势：拉一个区域。高亮带横穿它并越出画布——记号是「做过的事」，不是「画好的边」 |
| **B · 记号** `THE MARK` | 留下的**那一笔** | 产品以它画下的东西命名。五项能力最后都收敛成同一个物件：被标住、并且被留下的东西 |
| **C · 浮面** `STACK` | 留下的**那一叠** | 已落地的 FILM 语言正面看：截图浮层、贴图、剪贴板面板、用量面板，是同一物件在不同深度上的四次出现 |

C 直接继承产品已落地的设计语言（2026-10-24 选定的 B1「浮层优先 FILM」，见 `design-demos/theme-2026/direction-approved.md`），所以它和界面是同一套语法，不是另起一套。

### 1.2 底板为什么是深墨色，不是品牌琥珀色

这是整个设计里唯一一个**算出来而不是想出来**的决定，也是我一开始做错、被数据纠正的地方。

微软在应用图标设计页给了全平台唯一一条量化标准：

> "Make sure at least half of your icon passes a 3.0:1 contrast ratio on light and dark theme."
> — <https://learn.microsoft.com/en-us/windows/apps/design/style/iconography/app-icon-design>

把它当约束求解：一个像素要同时过 `#F3F3F3`（L=0.8963）与 `#202020`（L=0.0144）的 3:1，自身明度必须落在 **[0.1433, 0.2654]**。

第一版用的是明亮琥珀底板 + 浅色字形，三个方向全部不过。第一次修正是把底板压暗进那个区间——数字过了，但琥珀变成赭石，而且小尺寸分离度反而**变差**（A 的 sepDark 从 8.45 掉到 6.69）。这条路是错的，已废弃。

真正起作用的变量是**极性**，不是明度——因为标准按**面积**算，占多数面积的那个元素决定成败：

| 颜色 | 对白底 | 对深底 `#202020` |
|---|---|---|
| `--ink` `#1D1A16`（深墨） | **15.62 : 1** | 1.06 : 1 |
| `--primary` `#E5A44C`（琥珀） | 1.94 : 1 | **7.56 : 1** |

两者恰好互补。所以：**深墨占大面积当底板，琥珀只做记号** → 两个主题同时过线，且**品牌琥珀原封不动保留**。实测 A 在 16px 是 56% / 51%（浅/深），通过。

> 这也解释了一个反直觉的结果：浅色背景上，**最亮的那个颜色反而是对手**。琥珀做底板时它在白底上只有 1.94:1，等于自己消灭了自己。

### 1.3 16px 的四条硬规则（都是测出来的）

全部在真实 16×16 光栅上判断，不看 256px 母版：

1. **16px 只装得下「一个实心形 + 一个反形」。** 两个等重的形会互相抵消。四角括号在 16px 会并成一个「+」（v1 的 A1 已废弃）。
2. **记号不能用描边。** 32u 的条加一圈描边，描边会吃掉一半。记号一律是填充。
3. **45° 斜笔在 32px 以下会被锯齿打散成一串台阶。** 所有边都改成轴对齐。
4. **几何落在 256 网格上、承重边取 16 的倍数**，这样 16×16 是「同一张图画在像素格上」，而不是「一张大图被平均下去」。

底板圆角 58u（≈22.7%）也是按这条定的：16px 时正好落在 3px，这是让 16px 方块仍然读作「应用磁贴」而不是「窗口」的关键。

### 1.4 我删掉了哪些装饰，以及为什么

第一版有 16u 的上缘高光和底板微渐变——这是应用图标的常见装点。但在深墨底板上，那道高光是横贯顶部的一条**亮带**，对浅色主题恰好是反向极性。消融实测（`tools/ablate.mjs`）：

| 变体 | 浅色 | 深色 | 最差 |
|---|---|---|---|
| 有高光 | 50% | 50% | 50% |
| **无高光** | **56%** | **51%** | **51%** |

它是在**扣**通过率，不是加。所以直接删了，而不是调淡。渐变同理，只值约 1pp，一并去掉。

## 二、配色方案

### 2.1 主色（推荐）

| 角色 | 值 | 来源 | 用途 |
|---|---|---|---|
| **主色 · 琥珀** | **`#E5A44C`** | 产品 `--primary` 默认值 | 记号：高亮带、笔画、浮面 |
| 主色 · 亮 | `#F0B76A` | `--primary` 提亮 | 记号渐变上端 |
| 主色 · 暗 | `#D68F2E` | `--primary` 压暗 | 记号渐变下端 |
| **底板 · 深墨** | **`#1D1A16`** | 产品 `--ink`（浅色端） | 底板主体 |
| 辅助 · 米白 | `#F9F5EC` | 产品 `--surface` | 需要反形时（如 A 的取景框） |

**图标没有引入任何新颜色。** 每一个值都是 `shared/tokens.css` 里已有的 token。这是刻意的：图标应该是这套 token 的「第五个表面」，而不是在设计系统旁边另开一套。

### 2.2 为什么是琥珀

- 产品里 `--primary` 默认就是 `#E5A44C`，用户还能在设置里改。图标跟着走即可，不需要第二套决策。
- 琥珀在深色任务栏上 7.56:1，是深色场景里少数几个能既显眼又不刺眼的暖色。
- 与同类的差异是真实存在的：Snipaste 是四色拼块、ShareX 是三色圆环、Flameshot 是紫盘、PowerToys 是米色板、CleanShot X 是深灰板 + 蓝纸。**暖琥珀 + 深墨**这一组在 7 个样本里没有重样的。

### 2.3 深浅背景适配

| 背景 | 处理 |
|---|---|
| 浅色任务栏 `#F3F3F3` | 深墨底板 15.62:1，天然成立 |
| 深色任务栏 `#202020` | 琥珀记号 7.56:1 撑住内部；底板边缘靠轮廓分离（见下） |
| 白色窗口 / 浅色资源管理器 | 同浅色任务栏 |
| 纯黑 `#000000` | 底板 1.06:1 会融掉，靠琥珀记号识别 |

深底上底板本身会与背景接近（1.06:1），这是**所有深色底板图标共同的问题**，实测竞品区间就在这个量级（CleanShot X 底板底边 1.64:1、Flameshot 紫盘 2.27:1）。缓解手段是让**内部记号足够亮**（7.56:1），而不是把底板刷亮——刷亮就丢了浅色场景。

### 2.4 若要跟随用户改主色

用户在设置里改 `--primary` 时，只换记号那三个琥珀值，底板 `#1D1A16` 不动。只要新主色在深底上 ≥3:1（绝大多数中等明度彩色都满足），极性结论不变。

## 三、三方向对比与选择建议

### 3.1 实测数据

微软标准（≥50% 面积 ≥3:1，两个主题都要过）在 16px：

| 方向 | 浅色 | 深色 | 最差 | 判定 |
|---|---|---|---|---|
| **A 取景框上的记号** | 56% | 51% | **51%** | **通过** |
| B 记号 | 64% | 44% | 44% | 未过（深色） |
| C 浮面 | 68% | 44% | 44% | 未过（深色） |

A 在 16 / 24 / 48px 三档全部通过；128px 为 47%，差 3pp。

结构可辨性（`verify.py`，16px）：

| 方向 | avgStep | qSpread | 读得出什么 |
|---|---|---|---|
| A | 0.092 | 0.007 | 「两段条 + 一道横杠」——框的立柱塌成 1–2px 抗锯齿，20px 才恢复「框」 |
| B | 0.075 | 0.004 | **两竖两横 + 四个计数孔，结构完整** |
| C | 0.038 | 0.115 | 只剩一个黑坨，第二层浮面 32px 以下不存在 |

- **A 赢在**：语义最直白（截图/录屏/贴图三件都指向它）、深色任务栏最稳、面积标准通过。
- **B 赢在**：16px 结构最清楚，是唯一最小尺寸还在「讲结构」的；代价是语义最抽象。
- **C 赢在**：融合叙事最强、轮廓不对称；代价是最小尺寸叙事失效。

### 3.2 推荐

**推荐 A**，理由不是它最好看，而是它的**代价最小**：

- 五项里它直接讲清了三项（截图、录屏、贴图都是「先取一块」）；
- 唯一通过微软量化标准的方向；
- 深色任务栏上不「空」也不「异类」——把 C 放上去会读成一个空心环（中央与任务栏同色），B 则偏闷。

**如果你更看重「记忆点」而非语义**，选 B——它在 16px 的辨识度确实是三个里最高的，而且色块即品牌。

**C 不建议单独使用**：32px 以下它的叙事完全消失，只剩一个不对称黑块。

### 3.3 已知不足（诚实列出）

1. **A 在 16px 的「框」会塌。** 需要给 16px 单独出帧：立柱对齐整像素、高亮带 3px→2px、圆角 58u→3px 重画。现在的 16px 是 256 缩下来的，不是单独画的。
2. **A 的通过率有相当部分来自那个亮色取景框**（它同时是亮元素又占地），不是纯靠「形」。这是它的结构事实，不是缺陷，但要知道。
3. **三个方向都没有讲满五项。** 微软自己的规范写「最多两个隐喻，一个更好」——五功能塞进一个 16px 图标本来就不该是目标，**融合应该发生在动作层，不是符号层**。
4. 深色背景上底板边缘只有 1.06:1，靠内部记号识别。这是深色底板路线的固有代价。

## 四、落地（选定方向后）

现在**没有改动 `assets/`**。选定后需要：

1. 把对应的 `out/final/ico/highlighter-X.ico` 复制为 `assets/icon.ico`；
2. 重新生成 `assets/icon.png` / `assets/icon-dark.png`（托盘用，见 `main/services/tray-icon.js`——托盘本来就分 light/dark 两份资产）；
3. 复核 `test/tray-menu.test.js` 等相关断言；
4. 按 AGENTS.md 跑 `npm test` 与 `npm run check`。

`.ico` 已包含 **16 / 20 / 24 / 32 / 40 / 44 / 48 / 64 / 96 / 128 / 256** 十一档。20/40 对应 Windows 11 的 125%/150% 缩放，44 是开始菜单磁贴，96 是 400% DPI——现有 `assets/icon.ico` 只有 7 档，缺的正是这几个。

## 五、复现

全部产物由脚本生成，可直接重跑（从仓库根目录，需要 `node` + 仓库内 `playwright` + Python `Pillow`）：

```bash
node design-demos/app-icon/tools/final.mjs            # 出三方向的 SVG 与全尺寸 PNG
node design-demos/app-icon/tools/sheet.mjs            # 评审板 out/final/sheet.png
node design-demos/app-icon/tools/context.mjs          # 真实环境图 out/final/context.png
python design-demos/app-icon/tools/acceptance.py      # 微软 3:1 标准实测
python design-demos/app-icon/tools/verify.py          # 结构可辨性指标
python design-demos/app-icon/tools/pack.py            # 打包 ICO
```

探索过程的脚本也保留在 `tools/` 里，每一个对应一次被推翻的假设：`probe*.mjs`（形）、`plate-sweep.mjs`（底板明度）、`polarity.mjs`（极性）、`ablate.mjs`（装饰消融）、`twoasset.mjs`（双套资产）。删掉它们就等于删掉了「为什么是现在这个答案」。
