# Highlighter 功能增补分析：参考 Snow Apps 1.3.9

日期：2026-10-25（Asia/Hong_Kong）  
性质：产品与工程分析；仅新增本报告，不修改产品代码。

## 1. 结论与推荐顺序

**Highlighter 最值得补的是“截完以后少走几步”的能力：保存后直接使用、重复区域快速捕获、截图成品美化、局部放大标注，以及录屏裁剪与 GIF 导出。**

这些方向能复用已有截图、历史、标注和编码链路。相比继续扩充模型供应商、引入完整图片编辑套件或迁移 GPU 引擎，更容易形成可见收益，也更符合当前项目对常驻资源占用的要求。

建议顺序：

1. **先验收当前“历史继续编辑”改造**，固定文档、版本和保存契约。它已经在工作区实施，不能再次按空白功能立项。
2. **第一批：保存结果快捷操作 + 选区复用与尺寸预设。** 高频、范围较小，优先减少操作次数。
3. **第二批：截图成品预设 + 放大镜标注。** 提升截图用于说明、教程、反馈时的表达能力。
4. **第三批：录屏头尾裁剪 + GIF 导出。** 让录制结果无需转到其他软件处理即可使用。
5. 拼图/切分、贴图工作组、识别纠错、自动滚动等按实际使用场景再排；MCP 与新渲染后端暂不进入上述批次。

这里的优先级是依据工作流连续性、现有工程复用程度与资源成本作出的判断，**不是用户行为统计的结论**。本次没有使用频率或付费意愿数据。

## 5. 重点功能的建议范围

### A. 保存后直接使用：小投入，先做

**参考点。** Snow 的保存结果组件提供继续编辑、复制图片文件、复制路径、打开文件夹；表格识别可直接打开到系统表格应用。相关入口是 `screenshotsaveresult.cpp`、`ScreenshotRecognitionSessionController::openSpreadsheetFile()`。

**Highlighter 的增量。** 现有保存器已经处理默认目录与覆盖确认，历史页也有打开、复制和“地址”。缺口是这些动作没有统一接在刚完成的导出结果后面。

建议保存成功后展示轻量结果条，提供“打开”“地址”“打开文件夹”；编辑器场景保留“继续编辑”。表格新增“保存并打开”，交给系统默认应用处理，不绑定 Excel。快捷复制截图仍按原设置结束，结果条不应给每次截图增加必经步骤。

首版不包含 Windows 文件对象剪贴板与完整导出任务中心：复制图片像素、复制路径、复制文件对象是三个不同能力，后者需另做剪贴板格式与生命周期验证。多个任务先给按钮 loading、防重复提交和明确失败反馈即可。

**接入。** `image-file-save`/识别导出返回结构化结果 → 主进程绑定已保存文件 → 受限 IPC 执行动作。复用历史页“地址”的既有语义，不改成“定位”。文档保存与外部文件导出分开报告结果：文档提交成功不能被外部导出失败误报成全部失败。

**验收。** 取消保存不显示成功；文件被移动后明确报错；未配置表格默认应用时能提示；后台完成不抢焦点；批量任务的结果与实际文件逐一对应。

### B. 重复区域与精确尺寸：高频基础能力

**参考点。** Snow 已有选区数值与比例设置、quick set、历史区域导航；1.3.2 之后还新增了录屏区域历史快捷操作。

**首版。** “复用上次区域”、宽高输入、1:1/4:3/16:9 比例、自定义命名预设。先只保留一个最近区域与少量尺寸预设；完整历史浏览放到后续。

**接入。** 新建独立的区域偏好数据，保存屏幕标识、坐标单位、捕获时缩放和边界；截图与录屏复用同一归一化函数。不要仅依赖截图历史条目：历史关闭、记录被删除后，区域预设仍应可用；当前文档的 `crop` 是底图像素范围，也不能直接当作桌面区域。

**边界。** 显示器拔出、负坐标、DPI 改变后，区域要重新校验并回退到可见屏幕。录制开始后禁止通过区域历史修改正在录制的边界。

**验收。** 同一屏反复捕获尺寸一致；100%/150%/200% 缩放不漂移；显示器重排不产生屏外窗口；预设不影响现有 Escape 和快捷键行为。

### C. 截图成品预设：先做输出样式

**参考点。** Snow 的 `ScreenshotSelectionParams` 有圆角、阴影、背景以及边框类型/颜色/宽度。Highlighter 的界面圆角和矩形标注圆角不等于成品图片效果。

**首版。** 提供原图、浅色卡片、深色卡片三个预设；允许调整留白、背景、圆角和简单阴影/边框。先在导出预览里调节，暂不做画布上的效果拖拽手柄、渐变背景库或任意形状选区。

**接入。** 在共同的图像合成出口处理，并把输出样式纳入文档内容与版本校验；复制、保存、贴图及 PDF 必须使用一致的成品图。保留干净底图供继续编辑，不能把效果重复烘焙进去。OCR 输入不应包含装饰性边框。

**成本说明。** 4–7 人日只针对上述预设版；旧报告的 10–14 人日包含更完整的交互与选区效果系统，不能把两者视为同一范围。

**验收。** 预览与实际 PNG 一致；透明 PNG 和 JPEG 的底色策略明确；阴影不被裁掉；同一记录重复保存不会累计加边框；重开仍可切回原图样式。

### D. 放大镜标注：比增加冷门图形更有价值

**参考点。** Snow 的 `MagnifierData` 明确定义源区域、镜头位置、倍率、形状与连接线。这是导出到图片里的标注，不是取色器旁的临时像素放大镜。

**首版。** 框定源区域、移动矩形放大窗、选择 2×/3×/4× 倍率、简单边框和可选引线。暂不做旋转、多形状、渐变连接或自动排布。

**接入。** 新增标注类型时，同时覆盖 `shared/capture-document.js` 的类型白名单/校验、源像素坐标、命中测试、移动、撤销、持久化与导出。只加一个 Canvas 绘制分支无法完成“可再编辑”。采样缓冲按源区域和内容版本缓存，避免拖动时重建整张 4K 图。

**必须提前定义的行为。** Snow 的实现声明从原始底图采样。Highlighter 当前识别链也使用未叠加标注的底图（`capture/capture.js:2828`）。若用户用马赛克遮挡了内容，放大镜不能再把原像素露出来；需先定义统一遮挡规则与绘制顺序。普通马赛克也不能自动等同于不可逆的隐私擦除。

**验收。** 裁剪、DPI 与缩放后源区域准确；删除/撤销可恢复；保存重开仍能调整；被遮挡区不被放大镜绕过；限制多个镜头的缓存总量。

### E. 录屏剪头尾与 GIF：功能收益大，但须独立成批

**参考点。** Snow 把裁剪会话独立于录制窗口，支持范围预览、变速与重复导出，文档见 `snow_shot/docs/recording-trimming.md`。可借鉴会话职责，不必搬入其完整原生媒体引擎。

**当前基础。** Highlighter 已有停止后的预览、WebM 临时文件、MP4 转码、进度和会话清理。`RecordingService.transcode()` 当前限制输出 `.mp4`，`buildFfmpegArgs()` 固定 H.264 参数。因此基础编码组件具备能力，产品端仍缺裁剪范围、格式选项、预览同步和导出契约。

**首版。** 头尾两个裁剪点、所选范围播放、MP4/GIF 两种输出、GIF 帧率与宽度预设、进度与取消。变速可在同一服务扩展后追加；APNG/WebP、多段拼接、转场、摄像头和 HEVC 不纳入首版。

**接入。** 原始录制文件保持不可变；导出任务捕获提交时的裁剪参数；编码到临时文件，成功后发布结果。取消只清理该任务产物，导出失败允许重试，预览关闭与原始文件清理的时机需要显式约定。GIF 使用调色板流程；音视频裁剪应同时处理时间戳。相关机制见 [FFmpeg 官方滤镜文档](https://www.ffmpeg.org/ffmpeg-filters.html)。

**资源。** 一次只允许一个重编码任务；限制 GIF 时长、宽度、帧率与预计帧数，实际阈值由样本基准决定。不得为了进度预览把视频全部解码进 JS 内存；导出结束退出 FFmpeg。

**验收。** 有声与无声录制、非关键帧起点、短片段、取消和重试、重复导出、磁盘写入失败；MP4 音画同步且未破坏源文件，GIF 循环与时长正确。仅检查命令行参数不够，必须解码检查真实产物。

## 6. 第二梯队：有价值，但先收窄范围

### F. 拼图与长图切分

Snow 的拼图模型支持横向、纵向、自定义布局和 PDF，切分模型支持方向、等分/精确、像素/百分比。Highlighter 首版只需历史多选后按横向/纵向拼接，提供排序、等宽/等高、间距和背景；长图按固定高度或页高切分，并允许少量重叠。

拼图预计 4–7 人日，切分预计 2–4 人日，两项可独立交付。入口复用历史选择与长截图结果，主进程用现有 `sharp` 管线；只有预览缩略图进入渲染层。批量导出已有，不应重新搭建一套历史系统。自动避开文字行的智能分页留到后续。

大图是主要风险：当前 `LongCaptureSession` 允许最多 2 亿像素，单份 RGBA 理论上约 763 MiB，实际峰值还包含解码与中间结果；不能因为“用 sharp”就宣称低内存。必须做输入总像素限制、输出预估、队列并发限制，测量原生进程与主进程峰值。验收分片不漏行、不重复、顺序正确，取消不留下半成品。

### G. 贴图工作组与重启恢复

Snow 有独立 `PinnedWindowGroupManager` 与持久化仓库；Highlighter 目前主要管理活跃贴图窗口，已有 20 张上限。值得增加的是“把当前参考图保存为一个工作组”，并在需要时恢复位置、缩放、透明度和旋转。

先只做命名组、保存布局、手动恢复/切换、缺失图片提示。恢复需验证显示器位置；只创建当前组需要的窗口，不应启动时一次恢复所有组。持久化图片必须有明确所有权：若直接引用历史图片，历史清理后可能无法恢复，因此需资产引用计数或组拥有的副本，并接入数据目录迁移与清理。

优先级低于 A/B：它对经常多图对照的人有帮助，但每个 Electron 贴图窗口都有实际内存成本，本次没有测出每窗数值。

### H. 识别结果选择与轻量纠错

Snow 的识别会话支持文本编辑和表格编辑提交。Highlighter 已有 OCR 叠加、纯文本结果区与表格格式输出，不能写成“目前不能编辑任何 OCR 文本”。真正的增量是行级多选、只复制所选行、保留明确阅读顺序，以及表格单元格修正后同步生成 TSV/CSV/XLSX。

首版不做完整电子表格、公式计算或复杂合并单元格 UI。纠正结果应只有一个结构化数据源，避免表格显示已改、复制与导出仍使用旧字符串。大表格限制 DOM 数量；空值、前导零、长数字与引号/换行需回归。

可另行探索“搜截图里的文字”：当前历史过滤器会读取 `tags/ocrText`，但本次未找到完整的自动提取、回写与索引工作流。**这属于基于 Highlighter 现有能力推导的增强，非本报告确认的 Snow 差异项。** 如果推进，优先复用用户主动 OCR 的结果，避免默认后台识别所有截图造成常驻负担。

### I. 长截图自动滚动

Snow 的 `ScreenshotScrollingAutoScroller` 支持滚动间隔、方向、暂停和启停；Highlighter 现有长截图有拼接与首尾裁剪，未找到自动滚动注入的完整入口。

首版只针对明确选中的滚动容器，允许速度调节、暂停和立即停止；检测重复帧/到底后结束，保留手动模式。焦点改变、用户手动操作、窗口关闭时要停止注入；采集与拼接处理不过来时减速，不能无限堆帧。

这不是“加一个定时器”的小功能。浏览器、聊天窗口、设置列表、固定页头、懒加载和权限差异都可能改变结果；必须有应用样本矩阵，所以排在低风险输出增强之后。

### J. 录屏动作提示

Snow 近期补充鼠标滚轮效果，已有点击、光标和键盘效果链路。Highlighter 已有录制中标注，但那需要操作者主动绘制。

首版建议仅点击波纹、滚动方向和快捷键组合提示，明确开启后仅在录制期间采集，不记录完整普通文本。为事件记录统一时间轴，暂停后正确重映射；后续裁剪时沿用源时间。避免先做一套只能实时烘焙、之后无法正确裁剪的效果实现。

### K. MCP：保留方向，先验证真实用途

Snow 已提供 stdio MCP，具备会话、revision、异步 operation 与取消等契约。这比暴露几个截图函数复杂得多。

只有在确实需要“自动截图 → 标注问题 → 导出证据”时才投入。先设计状态、区域截图、OCR、保存、取消五类受限操作；默认关闭、以本地客户端为边界、显式管理会话所有权和产物路径。当前文档版本体系稳定后再接，不能允许自动化覆盖用户正在编辑的现场。

2–3 人日只够设计验证与小原型，**不是完整可发布 MCP 的估价**。当前没有自动化使用频率证据，不建议因 Snow 有该能力就把它排进近期主线。

## 7. 现阶段不建议跟进的内容

| 方向 | 当前不优先的原因 | 重新考虑的条件 |
|---|---|---|
| 迁移 Qt / Rust / GPUI 绘图栈 | Snow 的 retained GPU renderer、像素 lease 和智能擦除 GPU 优化是其架构演进；迁移会影响 IPC、打包、文本、输入与渲染一致性 | 有基准证明当前 Canvas 路径无法满足明确大图目标，且局部优化无效 |
| 内容感知智能擦除 | 模型/算法、纹理质量与资源成本都明显高于对象删除或遮挡 | 有足够频繁的修图需求与固定质量样本 |
| 完整拼图/切分编辑器、多形状选区 | 容易把效率工具扩成图片设计软件 | 轻量版真实使用表明需要复杂排版 |
| 摄像头合成、硬件 HEVC/HDR | 增加设备和编码后端矩阵；当前录制产物的基本处理更值得先补 | 有持续教程录制需求且 MP4/GIF 闭环稳定 |
| 更多 AI 供应商按钮、照搬所有模型参数 | Highlighter 已有多供应商路由，新增配置不一定减少用户操作 | 有具体协议不兼容或明确模型能力需求 |
| 因上游支持而扩展 macOS/ARM64/商店发行 | 属于平台与发行战略，不能作为普通功能迁移处理 | 独立确认目标用户、维护预算和设备验收能力 |

建议借鉴数据模型、交互和任务生命周期，在现有架构中实现；Snow 是多项目、多许可证仓库，且 Qt/C++/Rust 代码不能直接作为 Electron UI 模块搬入。本报告不提出源码整体迁入方案。

## 8. 实施依赖与资源验收

| 层次 | 建议约束 | 原因 |
|---|---|---|
| 文档模型 | C/D 的样式或新标注必须同步进入 schema、校验、内容指纹与旧记录兼容 | 防止保存重开丢功能或重复加效果 |
| 主进程/IPC | 路径由主进程解析；渲染层提交会话/记录 ID 与受限参数 | 复用当前边界，避免新导出功能绕过现有安全与版本控制 |
| 异步任务 | 明确 queued/running/succeeded/failed/cancelled；结果绑定提交时参数 | 当前 UI 状态改变不能篡改正在执行的任务 |
| 保存与数据生命周期 | 临时输出成功后发布；失败可重试；副本、版本和贴图资产参与保留/迁移/清理 | 功能闭环包括重启、删除与迁移 |
| 资源 | 无新增常驻编码器或后台 OCR；重任务排队；窗口按需创建、空闲释放 | 新功能主要增加活跃时负担，而不是持续抬高待机占用 |

验证应复用 `main/services/performance-monitor.js` 的进程指标，并补充 FFmpeg/原生进程与临时磁盘读数。不能只看 JS heap 就认定资源稳定。

建议记录修改前后同一场景的冷/热启动时间、交互 p50/p95、总内存峰值、任务结束后的回落、子进程存活与临时文件数量。样本至少包含普通截图、4K 图、多标注图、长图、短/长录制及多个贴图。数值阈值应先测基线再冻结，本报告不编造当前内存或帧率。

新增功能应只运行相关单元/契约/运行时检查，发布阶段再执行仓库要求的门禁。可见实机窗口默认放副屏；没有副屏时先确认。当地测试通过不能推断 CI 通过，也不能用组件能力检查替代安装包验收。

## 9. 可执行的排期建议

| 批次 | 内容 | 退出条件 | 人日粗估 |
|---|---|---|---:|
| 0 | 当前历史继续编辑收口 | 打开、编辑、更新/另存、失败重试、删除/迁移有验收证据 | 本报告不重复估算 |
| 1 | A 保存结果操作 + B 区域复用 | 常见路径少操作、保存结果可信、多屏区域不漂移 | 5–9 |
| 2 | C 成品预设 + D 放大镜 | 预览/导出一致、重开可编辑、遮挡规则明确 | 9–15 |
| 3 | E 裁剪 + GIF | 实际产物正确、音画同步、取消/重试不破坏源文件 | 8–13 |

前三个新增批次合计 **22–37 人日**；预留约 30% 的集成与实机不确定性后，排期参考约 **29–49 人日**。这是范围清楚的 MVP 组合，不包括 F–K，也不建议一次性全部开工。每个目标单独提交、独立验证，发现使用收益不明显就停止扩展。

如果只选一个近期增量，建议 **A 保存结果快捷操作**；如果只选一个辨识度更强的新功能，建议 **D 放大镜标注**；如果重点投入录屏，则直接选 **E 裁剪 + GIF**。三者服务的场景不同，不需要绑定发布。
