## 2. C：成品合成的预览重绘与导出耗时

测量方式：真实 Electron 页面 + 真实 canvas。每次计时后调用 `getImageData(0,0,1,1)` 强制
光栅器完成，否则 Chromium 可能把画布保持为 GPU 延迟状态，计时就只测到命令提交。
每个用例 15 次计时 + 3 次预热。

| 场景 | 输入 | 产物尺寸 | 兆像素 | p50 | p95 | max |
|---|---|---|---:|---:|---:|---:|
| 4K + 深色卡片 | 3840×2160 | 4032×2364 | 9.53 | **15.5 ms** | **18.1 ms** | 18.1 ms |
| 4K + 浅色卡片 | 3840×2160 | 4032×2364 | 9.53 | 15.7 ms | 16.9 ms | 16.9 ms |
| 1080p + 深色卡片 | 1920×1080 | 2112×1284 | 2.71 | 5.1 ms | 5.9 ms | 5.9 ms |
| 1080p 原图模式 | 1920×1080 | 1920×1080 | 2.07 | **0 ms** | 0 ms | 0 ms |
| 几何计算（无分配） | 3840×2160 | — | — | 0 ms | 0 ms | 0.1 ms |
| **面板预览重绘**（4K，scale 0.0389） | 3840×2160 | 157×92 | 0.014 | **1.2 ms** | **2.0 ms** | 2.0 ms |

**读数**：

- **原图模式确实是零成本**（0 ms，函数直接返回 null 让调用方沿用内容画布）。这与交接文档
  "原图等价"的设计主张一致 —— 不是"很快"，是**没有这段代码路径**。
- **4K 成品导出 p95 = 18.1 ms**（9.53 MP）。这是一次性导出成本，不是每帧成本。
- **面板预览 1.2 ms / p95 2.0 ms**，远低于一帧 16.7 ms 的预算，所以拖滑块时的预览重绘不会掉帧。
- 深色与浅色卡片差异 < 1 ms，说明阴影 alpha 不是瓶颈（几何相同，只有颜色不同）。
- 几何纯计算 p95 = 0 ms（200 次采样），符合"不分配画布"的设计。

> 未验证：真实 4K **照片**（非合成渐变）。合成内容可能比真实照片更容易被光栅器缓存或压缩。
> 这项偏低风险但未证实。

## 3. D：放大镜采样缓存与镜头重建

测量方式：真实 Electron 页面，4K 底图 + **8 个 blur 对象**（plan §7.1 的每文档上限，
也是采样底图的最坏情况）。冷样本 5 次；热路径 15 次 + 3 次预热。

| 场景 | 含义 | p50 | p95 | max | 样本 |
|---|---|---:|---:|---:|---:|
| 采样底图冷构建（4K + 8 blur） | 文档变化时**一次** | **8.1 ms** | 8.5 ms | 8.5 ms | 5（冷样本） |
| 镜头移动（同源区，新 lensOrigin） | 拖动时**每帧** | **0 ms** | 0.1 ms | 0.1 ms | 15 |
| 改源区（真重采样，复用底图） | 改框时**每次手势** | **0 ms** | 0.1 ms | 0.1 ms | 15 |

**缓存账**（同一轮真实采样后读取 `cache.stats()`）：

| 指标 | 值 |
|---|---|
| 镜头移动后缓存命中 | hits 18 / misses 1（首次采样后全部命中） |
| 改源区后缓存 | hits 3 / misses 15（每次新源区都是新键，符合预期） |
| 预算压力测试（10 个 1920×1280 = 9.4 MiB/个） | 保留 3 个 = **28.13 MiB** |
| 预算上限 | 32 MiB |
| 淘汰次数 | 7 |
| **是否守住字节预算** | **是**（28.13 ≤ 32） |

**读数**：

- **拖动镜头 p95 = 0.1 ms**，证明"移动镜头不重新采样"是真的（缓存命中，不是靠算得快）。
- **采样底图冷构建 8.1 ms**，只在改基图/改 crop/改 blur 时发生一次 —— 与"每帧都重建"相比，
  这是设计主张能否成立的关键，实测成立。
- **字节预算是真的按字节算的**：9.4 MiB 的条目在 32 MiB 预算里只能放 3 个，第 4 个会触发淘汰。
  按"条目数"记的缓存会在这里放 10 个（94 MiB）—— 实测证明它没有那样做。
- 冷样本只有 5 个，**不构成 p95 的统计意义**；它只能说明量级是 ~8 ms。

> 未验证：**16 MiB 单文档字节上限**（`shared/capture-document.js`）与 8 镜头组合下的
> 序列化体积没有单独测；本轮只测了采样缓存，没有测文档 JSON 体积。

## 4. E：真实 ffmpeg 编码的耗时/内存/磁盘

测量方式：调用**真实的** `shared/recording-export-options.buildExportArgs()` 生成 argv
（不重写命令，避免"测的是另一条命令"），用与应用相同的 `spawn(ffmpeg, argsArray)` 形态执行，
25 ms 间隔采样 `tasklist` 得到进程工作集峰值。源素材用捆绑 ffmpeg 现生成（1280×720@30 + AAC），
裁剪范围取中段 60%，因此走的是 `-ss` + `trim` 滤镜的**解码裁剪**路径。
每格 **1 次**运行（每次都是重新生成源 + 一次完整编码），所以只有"单次实测"，**没有 p50/p95**。

| 用例 | 时长 | 墙钟 | 实时倍率 | ffmpeg 峰值内存 | 产物 | 临时 `.part` 残留 |
|---|---:|---:|---:|---:|---:|---|
| MP4 | 2 s | **832 ms** | 2.40× | **242.2 MiB** | 0.39 MiB | 无 |
| MP4 | 30 s | **1809 ms** | 16.58× | **346.3 MiB** | 6.08 MiB | 无 |
| GIF (15fps) | 2 s | **1356 ms** | 1.47× | **160.1 MiB** | 1.08 MiB | 无 |
| GIF (15fps) | 10 s | **2621 ms** | 3.82× | **440.8 MiB** | 6.24 MiB | 无 |

**读数**：

- **编码墙钟随内容复杂度，不随时长线性**（30 s MP4 只要 1.8 s，因为 `testsrc2` 是合成内容；
  真实录屏的码率与细节不同）。所以这组数字**不能**外推成"10 分钟录制要多久"。
- **ffmpeg 峰值内存 160–441 MiB**。GIF 10 s 比 MP4 30 s 更高（调色板 + 帧缓冲），
  说明 **GIF 是内存上的更重路径**，这与"GIF 有帧预算"的设计相符。
- **临时 `.part` 文件 4/4 用例零残留** —— 发布协议"失败只删本任务临时文件"在成功路径上
  表现为"成功后临时文件已被 rename 掉"，实测确认无泄漏。
- 磁盘增量恰好等于产物大小（0.39/6.08/1.08/6.24 MiB），说明没有留下中间文件。

> **未验证**（必须在文档里保留）：
> - **>10 分钟长录制**的编码耗时与内存（plan §7.3 明确列为实机项）。
> - **磁盘写满**时的失败路径（probe 未注入磁盘故障；单测里有故障注入，但不是真实 ENOSPC）。
> - **Electron 全进程**峰值（本探针只测 ffmpeg 子进程；Electron 主进程 + 渲染层未计）。
> - **结束后回落到基线**未测（只测了峰值）。
> - 每格 1 次运行 = 无 p50/p95，这一项在 plan §10.2 的口径下**仍未满足**，只是量级已知。

## 5. 复现方式

两个探针已入库（只读测量，不作为门禁）：

```bash
# C + D：真实 Electron + 真实 canvas（隐藏窗，不占屏）
cd /d/workspace/Highlighter
env -u ELECTRON_RUN_AS_NODE \
  TMP="D:/workspace/Highlighter/.tmp-perf" \
  TEMP="D:/workspace/Highlighter/.tmp-perf" \
  node_modules/electron/dist/electron.exe --no-sandbox scripts/probe-cde-performance.js
#   -> .tmp-perf/cde-performance.json

# E：真实 ffmpeg 编码（纯 node，无需 Electron）
node scripts/probe-cde-export-performance.js
#   -> .tmp-perf/cde-export-performance.json
```

`.tmp-perf/` 已被 `.gitignore` 的 `.tmp*/` 覆盖，产物不入库。

**探针设计上的两条教训**（写在这里，避免下一轮重复踩）：

1. **不要把整轮测量放进一个 `executeJavaScript`**。第一次实现把 4K 建图 + 15 次合成放在同一个
   page script 里，`executeJavaScript` 没有进度通道，宿主超时后**一行输出都没有**，看起来像死锁。
   现在每一步一次往返，卡住能定位到具体哪一步。
2. **计时后必须 `getImageData(0,0,1,1)`**。否则 Chromium 可以把画布留在 GPU/延迟状态，
   计时只反映命令提交，会得到"4K 合成 0 ms"这种明显不真实的数字。

不得把本文件当作"性能验收通过"。
