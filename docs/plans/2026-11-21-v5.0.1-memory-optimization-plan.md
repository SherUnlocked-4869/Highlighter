# Highlighter 5.0.1 内存优化方案

2026-11-21 · 设计评审稿。依据本机已安装的 5.0.1、运行日志和两份调研。已比对截图、显示诊断、剪贴板、OCR、划词和依赖装配等关键文件，安装包与当前仓库对应文件的内容一致。

**先确定截图和窗口渲染结束后 GPU 进程仍持有哪些分配，再压低截图峰值与纯托盘基线。** 本机 GPU 进程约占七进程私有提交的 57%、私有工作集的 52%。剪贴板面板已有回收机制，首轮只验收其实际行为。

延续 [原内存优化方案](2026-10-26-memory-optimization-plan.md) 中的窗口角色、空闲回收和图片预算设计。

## 1. 两份调研的结论复核

### 当前占用

现有会话关闭主窗口后，连续 13 次采样约 65 秒，七进程合计约 **217 MiB 私有工作集、476 MiB 私有提交、676–677 MiB 工作集之和**。GPU 进程约 **113 MiB 私有工作集、269 MiB 私有提交**，主进程约 **62 / 108 MiB**，划词监听约 **21 / 63 MiB**。此时没有界面渲染进程，采样期间 CPU 接近零，内存基本持平。这个水平对使用后回到托盘偏高，短时间的稳定只能说明这段采样没有明显上涨。

任务管理器默认内存列通常反映私有驻留内存。私有提交包含可由 RAM 或分页文件支持的内存，逐进程工作集之和则可能重复计入共享页。报告中的约 505 MiB 是按若干进程工作集相加，不能据此还原用户当时看到的列，也没有建立纯托盘冷启动基线。空白 Electron 和其他截图工具的数字缺少同机、同场景、同计数器的对照，250–300 MiB 可以在获得基线后讨论为产品目标。 [Microsoft 内存诊断指南](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-memory-leaks) · [Windows 工作集定义](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set)

## 2. 实施顺序

### 第一批 · 建立可比较的基线并定位 GPU

1. 扩展现有快照工具。外部采样按安装目录与根 PID 追踪进程树，从 Windows 计数器采集私有工作集和私有提交，同时记录总工作集、CPU、进程数、专用 GPU 内存与共享 GPU 内存。内部快照继续提供窗口角色和 Electron 子进程名称，通过 PID 和时点关联。显存单独呈报。 [外部快照脚本](../../scripts/memory-snapshot.js) · [内置性能快照](../../main/services/performance-monitor.js#L126)
2. 对齐关键时点。记录捕获开始、后端返回、编辑器首帧、截图窗销毁、首页首帧和各自空闲点。每次只记录后端类型、回退原因类别、尺寸、PID 和耗时。追踪只在内部诊断时短时开启，日志不采集图像或窗口标题。
3. 用相同 Release 构建、数据样本、显示器、刷新率、DPI、驱动和开关做独立会话。先测纯托盘，然后分别测只打开并关闭首页、区域截图后直接退出、截图后再打开首页、强制 Electron 兜底。把首页是否销毁和 GPU PID 是否更换一并记下。若只开首页也复现，进一步对照首页合成行为。若只在 Electron 兜底复现，优先处理采集。若两种采集后端在编辑器首帧后都复现，检查编辑器的图像纹理与合成面。
4. 对复现组做 Chromium MemoryInfra 追踪。比较采集返回、首帧、关闭和空闲的 Skia、合成和 SharedImage 分配。若分配主要出现在驱动或 Windows 图形层，保留系统计数器证据并用对应跟踪工具定位。阶段产物是可重复的对照曲线及至少一条有证据支撑的分配路径。 [Electron 追踪 API](https://www.electronjs.org/docs/latest/api/content-tracing) · [Chromium GPU 内存追踪](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/memory-infra/probe-gpu.md)

### 第二批 · 缩小已证实的抓取与驻留

- **诊断元数据按需获取。** 默认通过 `screen` 获取显示器几何。若需要 Electron 采集源 ID 和显示器映射，用 0 × 0 枚举。实际缩略图尺寸只在明确要求验证采集像素时获取。同步更新诊断返回契约、现有测试和探针，避免把屏幕尺寸解释成实际缩略图尺寸。 [Electron 采集 API](https://www.electronjs.org/docs/latest/api/desktop-capturer#desktopcapturergetsourcesoptions)
- **焦点窗口只捕获目标。** 先独立去除未消费的图标请求，再验证按 HWND 或已确认的源 ID 捕获一张图。目标身份在窗口焦点变化前获取。把报告提出的 BitBlt 作为候选，按遮挡、混合 DPI、跨屏、同标题、硬件加速窗口及窗口在请求期间消失等情况做真机对照。受保护内容沿用系统限制。现有捕获路径作为有时限的兼容兜底。新路径的失败反馈与兜底命中率进入验收。 [微软 GDI 捕获说明](https://learn.microsoft.com/en-us/windows/win32/gdi/capturing-an-image)
- **按第一批证据释放分配。** 兜底路径只在必要时请求图像并限制并发。若问题在编辑器或贴图，先减少重叠的全尺寸位图和纹理，确保退出、取消、转入贴图及失败时释放各自资源。4K RGBA 单份约 31.6 MiB。贴图可再试按资源 ID 读取原始编码图像，验证保存、复制、重新标注及 OCR 共享资源时的所有权。 [截图画布](../../capture/capture.js#L424) · [截图初始化缓冲释放](../../main/domains/capture/index.js#L674) · [贴图数据](../../main/domains/pin/index.js#L245)

### 第三批 · 降低纯托盘与低频功能成本

- **依赖按使用边界加载。** 分开处理 `sharp`、OpenAI SDK 和截屏模块。先移除托盘启动路径上的实际依赖加载，同时保留 AI 统一入口。把无需 SDK 的配置归一化从网络客户端路径分开，梳理长截图、历史缩略图和导出调用。原生显示器预热仍需要调查截屏模块公开方式和首次截图延迟。对照每个依赖改动的主进程提交、启动时间、首次截图、首次缩略图、首次 AI 请求以及打包版原生模块加载。 [架构检查](../../scripts/check-architecture.js#L94)
- **剪贴板只修复复现到的释放缺口。** 测普通隐藏、立即释放、快速重开和粘贴中触发计时。核实窗口及对应渲染器回落，粘贴完成后延迟释放生效，同时原生监听继续记录新复制。只有在某条路径超过配置超时仍持有资源时，再修该路径。
- **音频先做最小对照。** 用同一安装包分别测快门音开和关，再用测试构建比较关音时不创建媒体元素、开音时按需创建并播放。每组从新进程开始，记录 AudioService 首次出现和截图后的占用。按需加载能避免关音路径的媒体准备，开音播放仍可能启动 AudioService。只有收益稳定且声音时延达标，再比较 Windows 原生播放。录屏系统音和麦克风列入回归。
- **启动策略最后决定。** 划词分别测 UI 冷显和监听退出。工具条回收以选词到可点击的延迟与无闪白通过为条件，独立关闭划词时再退出监听。OCR 分别测开机预热直到 300 秒空闲、首次本地识别和再次识别，按整段延迟决定是否调整新安装默认值。已保存的用户设置参与原样回归。

## 3. 验收与发布条件

| 场景 | 记录与判定 |
| --- | --- |
| 纯托盘冷启动 | 新进程，30 分钟无交互。独立运行至少 5 次，用最后 5 分钟的中位数比较主进程和全树内存。记录开关、数据样本及实际后台进程，先做同版本重复测量，取得波动范围 |
| 4K/混合 DPI 区域截图、关闭 | 每次至少记录采集峰值、编辑器首帧和关闭后 1、5、15 分钟。第一指标是第 5 分钟 GPU 私有工作集与提交，改善须超出同版本波动。截图像素、定位和内容完整，交互延迟的允许变化按基线确定 |
| 30 轮重复截图 / 开关首页 | 分场景测试。记录每轮回到同一状态时的分配和进程数，比较平台水平及增长趋势。累计上涨需解释并复测。延迟报告标注样本数与 P50/P95，冷、热路径分别计量 |
| 窗口截图、诊断和大图贴图 | 核对 ID 与显示器映射、一张目标图、兼容兜底、多个 4K 贴图闭合后的回落，以及复制、保存、重新标注、OCR 的结果 |
| 剪贴板、划词、OCR 和录屏 | 检查关闭后回收、冷重开、快速重复触发、剪贴板回贴、划词首显、OCR 首次识别，以及录屏声音和导出，记录相应错误率和延迟 |

先把 30 分钟托盘基线纳入项目现有跑分的独立真机场景，日常跑分继续使用现有快速路径。可见测试窗口放在副屏，按项目约定保留主屏。基线重复稳定后，再在固定机器上用基线和允许波动建立门槛。每批可独立提交和回滚，发布前附同配置的前后对照以及复现步骤。当前资源快照支撑优化排序，节省量和验收阈值由实测确定。 [现有性能基准](../../scripts/benchmark-performance.js)

## 4. 首轮执行记录

- 快照工具按根 PID 和创建时间跟踪同一棵进程树。每次采样记录开始与结束时间，系统计数器缺失时显示为未取得。截图日志以 `captureId` 对齐 `capture.started`、`capture.acquired`、`capture.interactive`、`capture.closed`，就绪与关闭记录可用的渲染器 PID。 [采样工具](../../scripts/memory-snapshot.js) · [截图事件](../../main/domains/capture/index.js#L442)
- 显示诊断默认仅取采集源元数据，显式请求时才测量缩略图尺寸。真实 Electron 双屏验证了两条路径返回一致的源 ID 和显示器映射。焦点窗口截图移除了未使用的图标请求。GPU 测试在副屏进行，使用隔离配置。 [诊断实现](../../main/services/window-actions.js#L38) · [焦点窗口截图](../../main/domains/capture/index.js#L268)
- `sharp` 移到历史缩略图处理和长截图合成时加载。隔离开发版每组三次启动，采样时主进程私有提交中位数从 71.3 降到 65.0 MiB，工作集中位数从 162.1 降到 157.5 MiB。修改后启动阶段三次均未加载 `sharp`。该结果用于验证加载时机和主进程收益，打包版托盘基线另测。 [历史服务装配](../../main.js#L188) · [长截图按需加载](../../main/services/long-capture-session.js#L83)
- 原生抓屏对照使用同一副屏。仅取图时，GPU 进程私有提交从 108 MiB 升到 151 MiB，关闭隐藏首页 60 秒后为 149 MiB。另一独立会话进入截图编辑器时，GPU 私有提交从 159 MiB 升到 393 MiB，关闭截图与首页 60 秒和 300 秒后均约 382 MiB。两组各一次，启动值有差异，后续用重复对照衡量变化幅度。
- 单独一次 MemoryInfra 跟踪中，编辑器显示阶段 GPU 进程的 SharedImage 统计值从约 47 MiB 到 103 MiB，关窗后回落至约 0.3 MiB。同期 `malloc` 统计值则由约 39 MiB 升至 94 MiB，关窗后仍约 89 MiB，GPU 私有提交仍约 376 MiB。分类计数与进程私有提交采用不同口径。优先用受控对照检验编辑器合成峰值，以及 GPU 进程中持续驻留的原生分配。 [Chromium 内存归属说明](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/memory-infra/probe-gpu.md)

## 5. 第二轮执行记录

- **截图背景对照。** 在副屏的 125% 缩放下，用同一份 1440 × 2560 合成图对照背景 Canvas 与直接显示已解码原图。两版抽查的预览区域像素相同，完整导出与源图逐像素一致。直接显示原图未降低 GPU 私有提交。换成 4K 合成输入后，每组三次，进程树峰值私有提交中位数由现有路径的约 681 MiB 上升至原图直绘的约 712 MiB，GPU 进程对应中位数由约 468 MiB 上升至约 501 MiB。因此撤回原图直绘实验。4K 对照是在副屏缩放显示 4K 输入，未覆盖 4K 显示器全屏。继续用现有截图事件区分合成峰值与关闭后的原生分配。 [截图背景与标注画布](../../capture/capture.js#L402)
- **AI SDK 按需加载。** 保留统一 AI 入口，将 OpenAI SDK 的加载推迟到实际创建客户端。隔离启动每组三次，主进程私有提交中位数由 64.9 降至 60.1 MiB，工作集中位数由 131.4 降至 126.5 MiB。首次本地模拟模型目录请求的中位数由约 8 ms 增至约 58 ms，包含 SDK 首次加载开销。三次均通过无密钥本地目录请求。 [客户端工厂](../../main/services/ai/client.js#L94)
- **快门音按需配置音源。** 隐藏的截图页面和关闭快门音的路径不指定 WAV，启用时在显示回执后赋予音源，再播放一次。验证包含无音源的禁用路径、真实媒体解码、重复显示回执和 CSP。在快门音关闭、同一副屏与 1440 × 2560 合成输入的三组配对开发版测试中，仅切换音频元素的加载配置。旧配置三次都启动 AudioService，修改后三次都没有。截图窗关闭 5 秒时，Electron 进程树私有提交中位数由 501.1 降至 320.7 MiB，GPU 进程由 358.6 降至 190.2 MiB。该结果限于快门音关闭的场景和 5 秒采样点。 [快门音播放](../../capture/capture.js#L269) · [媒体元素](../../capture/capture.html#L261)

## 7. 后续落地与统一验收

- **截图**。Windows 焦点窗口优先用独立短生命周期进程获取前台 HWND，抓取一张图。检查窗口的显示保护、尺寸和空白结果。超时或图像不适用时，只有 Electron 源 ID 匹配原 HWND 才采用该缩略图。焦点窗口与区域截图的 Electron 兜底各限制为一次并发。原生显示器列表和 `screenshot-desktop` 改到首次实际抓屏时加载，显示器拓扑变化继续使列表失效。
- **贴图**。截图、文件贴图及长截图把 PNG 字节交给主进程持有的资源。编码字节的常驻预算为 32 MiB，超额时使用匿名临时文件句柄。复制、保存、重新标注与 OCR 按需读取同一份原图。替换、窗口关闭及渲染进程退出时释放资源。普通贴图绘制到像素画布后释放 Blob URL 和解码源，长截图保留显示所需的 URL 到替换或关闭。 [File API 的 Blob URL 生命周期](https://w3c.github.io/FileAPI/#lifeTime)
- **划词、剪贴板与 OCR**。划词工具条隐藏 5 分钟后回收，下一次选词重建。关闭划词即回收窗口，剪贴板历史仍开启时继续保留它依赖的原生租约协调进程。剪贴板面板重开复用同一个内存会话，实时按已隐藏时长应用新的释放设置，回贴事务完成后再执行到期释放。OCR 设置页提供启动预热开关，沿用已保存的偏好和现有默认值，按最终首次识别耗时决定是否调整默认值。

### 真机统一验收顺序

| 次序 | 操作 | 验收时记录 |
| --- | --- | --- |
| 1 | 基线版和优化版分别冷启动到托盘。配置、数据、显示器及驱动保持一致，每版新进程独立测至少 5 次，每次 30 分钟无交互 | 末 5 分钟主进程与全树的私有工作集、私有提交 P50/P95，同样保留 GPU 专用和共享显存、CPU 及进程数 |

| 3 | 焦点截图覆盖普通窗口、同标题窗口、部分遮挡、跨屏、窗口关闭及受保护窗口 | 内容和目标身份正确，裁切与尺寸符合预期，分别记录原生路径和 Electron 兜底的命中次数及延迟 |

| 5 | 等划词工具条隐藏 5 分钟后再次选词。关闭划词时分别开启和关闭剪贴板历史。修改隐藏面板的回收时长并测试回贴 | 工具条冷显延迟和闪白，原生监听随功能开关退出或保留，剪贴板记录与回贴继续可用 |

```powershell

```

命令每 30 秒采样一次，覆盖 30 分钟。JSON 保留原始进程样本及 `tail.main` 和 `tail.tree` 的末 5 分钟统计，缺失的计数器标为不可用。确认采样完整后，再以重复运行的差异设固定机器的回归门槛。若截图后仍存在持续的 GPU 驻留，按第 2 节采集 MemoryInfra，定位后再调整编辑器图像层。已试过的背景 Canvas 改 `<img>` 路径在先前对照中增加了驻留，因此当前采用验证过像素的 Canvas 路径。
