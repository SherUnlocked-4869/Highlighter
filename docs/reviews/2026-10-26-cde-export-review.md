## 1. Verdict

**Not safe to ship as-is.** The design is right and the parts the handoff advertises —
reference-lease instead of `cleanupSession`, decode-accurate `trim`/`atrim`, write-temp →
verify → atomic-rename, and a `publishing` state that refuses cancel — are genuinely
implemented and I verified them working (real 4 s/50 ms-range encodes land on the correct
frame, the user's file survives every failure I could inject, `target-changed` correctly
refuses a competing write). What is *not* safe is the arbitration and lifecycle layer around
those correct primitives: **the user cannot cancel a running export at all** (the only cancel
control is rendered `disabled` while the task is running — the shipped test suite never clicks
it, so this has never been exercised), a **cancel that lands during verification is reported
as `verify-failed` instead of `cancelled`**, **`dispose()` returns while a task is still inside
`publish()` and that task then publishes a file after shutdown has "finished"**, the
**target-snapshot re-check before the rename has a real TOCTOU window** (proven: a competing
write landing inside it is silently overwritten), and **`submit()` accepts a target equal to
the recording's own source path, replacing the user's recording with the trimmed output**.
Individually most are narrow races; together they mean the three promises the handoff makes
about E's concurrency (plan §8.4) are not all true, and two of them fail on paths a user hits
without any race at all. Everything found is fixable inside the existing design; nothing here
argues for restructuring.

Finding counts: **3 critical, 5 high, 4 medium, 3 low** (CONFIRMED), plus **2 SUSPECTED**
and **1 explicitly not checked**.

### 2.1 What the Lead's two questions resolve to

**(a) Path/argv edge cases — both are PROBE ARTIFACTS, not product bugs. Confirmed by reading the shipped path.**
- The argv builder never passes a bare relative name: `buildExportArgs` receives `outputPath` = `task.tempPath`, and `tempPathFor` (`recording-export-service.js:299-304`) does `path.join(this.path.dirname(targetPath), suffix)` on `absoluteTarget`, which `submit()` produced with `this.path.resolve(targetPath)` (`:200`). So element `[args.length-1]` is always an **FQ path** — a leading dash in the *basename* is safe (I re-verified: the shipped builder emitted `C:\…\与 空格 and spaces\-leading-dash.mp4` and ffmpeg wrote it fine; the failure in my scratch log came only from a deliberately *relative* `-dash-only.mp4`, which no code path produces).
- A double quote is **illegal in a Windows filename** (`ERROR_INVALID_NAME`), so the save dialog cannot hand one to `submit()` from a basename. The residual question the Lead raised — *can a directory in the path contain a quote?* — **no**: a quote cannot appear in any Windows directory name either, so such a target cannot exist on disk. `dialog.showSaveDialog` returns a path the OS accepted, and `fs.open`/`fs.rename` fail closed. **Ruled out.**
- I probed the reachable exotic cases on the shipped argv: spaces, CJK (`名字 带空格.mp4`), emoji (`emoji-🎬-clip.mp4`), `'`, `;`, `&` — **all encode successfully**. Emoji/CJK/space are the realistic set and none of them is a bug. The one *real* argv property worth recording as a **Verified sound** item: ffmpeg is spawned with `stdio: ['ignore','ignore','pipe']` and an argv array, never a shell string (`recording-export-service.js:462-465`), so shell metacharacters are inert by construction.

**(b) The GIF budget does NOT have an off-by-one, and an accepted request does not exceed the budget.** Measured with the decode-to-PNG-sequence method (`final-gif.js`) so the count cannot be corrupted by buffer limits:

| selection | fps | `estimateGifFrames` (shared) | actual decoded frame count | budget |
|---|---|---|---|---|
| 50 ms | 20 | 1 | **1** | 1200 |
| 100 ms | 20 | 2 | **2** | 1200 |
| 150 ms | 20 | 3 | **3** | 1200 |
| 200 ms | 20 | 4 | **4** | 1200 |
| 333 ms | 15 | 5 | **5** | 1200 |
| 1000 ms | 20 | 20 | **20** | 1200 |
| 10 s | 20 | 200 | **200** | 1200 |
| **60 s** | **20** | **1200** | **1200** | **1200 (exactly at the cap)** |

`estimateGifFrames` uses `ceil(duration*fps/1000)` with `max(1, …)` (`recording-export-options.js:185-191`); `trim` + `fps` + `paletteuse` emit exactly that many frames for a range shorter than the source, so the accepted boundary sits **exactly** on the budget with no off-by-one in either direction. Two honest caveats instead of an off-by-one: (i) the *earlier* `spawnSync`-based counts that appeared to show "5 frames for a 100 ms selection" were an artifact of `spawnSync`'s default 1 MiB `maxBuffer` truncating decoded `rawvideo` — **probe artifact, disregard**; (ii) a selection **longer than the source** silently produces a short GIF rather than an error, but `normalizeRange` prevents that (`range-out-of-bounds`), and my 30 s-request-on-a-10 s-source row only exists because I bypassed the validator in the probe.

## 7. Suggested fix order (smallest change, highest risk removed first)

1. **E-01** — one line (`trim-view.js:245`) plus a real test. Restores the user's ability to
   cancel, which also makes the rest of the cancel machine actually reachable/testable.
2. **E-02** — move the cancel check above the verify-failure branch (three lines). Removes a
   self-contradictory reported outcome on a path every user can hit.
3. **E-03** — reject `target === source` in `submit()` (three lines). Removes the only
   data-loss-by-normal-interaction finding.
4. **E-04** — make `dispose()` await `publishing`. Bounded, small, and it is the one place
   where the process can die mid-rename.
5. **E-06 / E-07 / E-08** — thread the real error code, fix queue admission ordering, gate on
   the coordinator *before* spawning. Each is local to `pump()`/`submit()`/`encode()`.
6. **E-11 / E-12** — relax the audio expectation for spans beyond the audio end; make
   `verify` check the container/codec it claims to check.
7. **E-05** — add a per-target single-flight guard and *document* the residual external-writer
   race honestly (the docstring currently promises more than `stat`+`rename` can deliver).
8. **E-09 / E-10 / E-13 / E-14 / E-15** — messaging and hardening; no data risk.
